# 中文小说 → 海外题材改写：开发计划

> 状态：设计稿 + **M0 / M1 已落地**（规则库 + 静态校验器，M2 起待做）
> 目标：把项目里已有的中文小说，改写成符合 Dreame / GoodNovel / Webnovel 英文短篇平台调性的可投稿作品。
> 依据：头条「超级话题·海外长篇定制」4 篇编辑干货 + 海外平台/出海服务商公开资料 + 本仓代码实测。

---

## 0. 结论先行

这件事**可做且值得做**，但形态必须定准：**不是「翻译器」，是「改写器」**。

三个已经用公开资料证实、决定产品形态的事实：

1. **本土化 ≠ 翻译。** 海外读者的判据是「像不像自己人写的」，标准在语言层 + 叙事层 + 套路层，不在字面准确。
   ——头条《海外"本土化"不是翻译？》：语言层（句长/词性/语气词/称呼/骂人/委婉）+ 叙事层（说破 vs 呈现、解释 vs 动作、心理描写克制、比喻克制、第一视角主动）。
2. **AI 翻译不能独当一面。** 昆仲科技 CEO 童晔：ChatGPT 有安全护栏会拒译暴力内容；大模型「读五千字后按理解重写一遍」导致大量漏译删减；上下文窗口有限 → 「200 万字中同一个人名翻译保持一致」做不到。
   ——知乎《网文出海进行时｜内容本地化是破浪关键》(2023-12-22)
   → 产品结论：**外挂术语表 + 静态一致性校验**是必须项，不是加分项。
3. **平台侧有硬性规格，且卡点很早。** 海外读者付费卡点在第 6-8 章，开篇前三章必须释放爽点。
   ——头条《副业赚钱海外网文投稿全攻略》(2026-05-14)

因此本功能的产品形态 = **诊断 → 确认 → 分级改写 → 质检** 四段式流水线 + 一套**可编辑的领域规则库**。

## 1. 调研结论

### 1.1 三大平台规格基线（⚠️ 二手来源，需用户在官方页复核）

来源：头条《副业赚钱海外网文投稿全攻略：写作套路+投稿渠道，一篇讲透！》(2026-05-14，原始出处「尽见商业研究局/大鹏」)，另一处为自媒体《AI写小说出海赚美金》(2026-08-19)。**两组数字互相矛盾**（全勤/签约奖/字数门槛），说明这类数字变动频繁且不可尽信 → **规则库做成用户可编辑的数据文件，不写死在代码里**。

| 维度 | Webnovel | GoodNovel | Dreame |
|---|---|---|---|
| 背景 | 腾讯阅文（出海最早） | 新阅科技（2020 上线） | 新加坡 Stary（2018 上线） |
| 全勤奖 | 200 美元/月 | 150 美元/月 + 100 美元签约奖 | 150 美元/月 + 50 美元签约奖 |
| 更新要求 | 日更 1500 字 | 月更 5 万字（日均 1667），满 25 天 | 月更 5 万字（日均 1667），满 28 天 |
| 签约方式 | 邀约制（门槛高） | 自主申请，满 5000 字可申 | 自主申请或邮件投稿 |
| 流量排名 | 第 1 | 第 2 | 第 3 |
| 推荐人群 | 有成绩的老作者 | 新手首选 | 想快速签约的新手 |

补充：GoodNovel 阶梯完结奖励 12 万字 250 美元 / 30 万字 1000 美元；部分平台写作竞赛奖金池 >50 万美元。

### 1.2 题材与套路基线

**女频**（侧重情感关系与身份地位反转）
- 狼人 Werewolf：ABO（Alpha/Beta/Omega）、狼群等级、标记与变身
- 亿万富翁 / 霸总：替嫁、先婚后爱、追妻火葬场、真假千金、带球跑
- ⚠️ 避坑：穿越 / 重生文化理解门槛高，新手不建议

**男频**（侧重成长体系与即时反馈）
- 系统流：经验值 / 等级提升 / 技能解锁，完读率比传统奇幻高约 37%
- 魔法、异世界、星际
- 硬规则：**每章结尾要有「任务—奖励」闭环**

**通用爽点公式**：配角看不起主角 → 主角低调/隐藏实力 → 大佬出面打脸 → 配角跪了
典型场景：同学会打脸、购物甩黑卡、真假千金反转、裁员裁到大动脉、追妻火葬场。

**头条编辑给的「狼人文」三组对照**（可直接做成改写规则）：
- 只写神通 → 技能展示；应写成升级**过程**承载生存压力
- 只写成仙过程 → 升级打卡；应让情感承压（师徒情、人物选择）
- 只写世界观 → 完整但没生命；应让设定参与人物命运
> 金句：「升级回答的是『他变强了多少』，成长回答的是『他变成了什么样的人』」

**头条编辑给的第一视角三大问题**（可直接做成静态校验规则）：
1. 太过被动：看到→感觉→反应→等待 ❌ / 看到→判断→决定→行动 ✅；每章给女主三样：目标 / 选择 / 行动
2. 自我观察违背：「第一视角是她的眼睛，不是上帝的眼睛」—— 写不了「我的脸红了 / 我的眼睛红了 / 我的表情 / 我的脸色」；可写：手、脚、衣服、感觉、心跳呼吸、声音、别人说的话、镜子里的自己
3. 赘述：重复感受 / 过度解释 / 无关回忆 / 内心独白循环 / 形容词堆叠

### 1.3 两套可直接复用的方法论

**A. SoloEnt「海外短篇网文本地化」插件 v1.0.0（2026-03-24）—— 直接对标本功能**
- 三步工作流：**诊断 → 确认 → 执行**；核心规则「不得跳过诊断与确认」
- **五维诊断** + **A/B/C 三档改写级别**：
  - A 小幅精修（5%–15% 改动）
  - B 西化改造（40%–60% 改动）
  - C 保留故事核的整体重建（80%–100% 改动）
- 按需加载文档：`style-guide.md`（语言层）+ `platform-guide.md`（平台层）+ 品类文档（`mafia-romance.md` / `werewolf-romance.md`）+ `quality-checklist.md`
- 输出必须带上下文标注：词数、POV、【改写说明】、「本次改写学习要点」

**B. drama-adapt-skill（GitHub `rorojiao/drama-adapt-skill`，MIT）—— 分阶段骨架**
- 五阶段 + **3 个人工确认节点** + 断点续跑（`project.json`）+ 质检报告（格式/叙事/角色，带评分）
- 启动向导先问三件事：**题材类型 / 规格 / 改编策略**（忠实 / 精简 / 创意）

**C. ZenStory AI（MIT，开源）—— 付费卡点「先定断点，再倒推」**
- 可用断点五类：已开始未完成的动作 / 证据持有人或解释权改变 / 关系从信任转为怀疑 / 抽象风险变成具体期限 / 两项都有代价的选择
- 倒推 5 步：① 写核心兑现 → ② 比较候选位置 → ③ 倒推免费段需要的处境/关系/证据/代价 → ④ 检查免费段已有局部进展 → ⑤ 写付费后第一段
- 6 条失败→修正对照（免费段只堆惨 / 断在普通台词中间 / 付费前已完成核心爽点 / 付费后换场拖延 / 连续提问没有答案 / 为卡字数硬拆场景）→ **直接就是校验规则表**

### 1.4 已有国内同类产品

中文在线「逍遥」海外作者平台：支持中文大纲生成地道英文，内置润色与情节续写，签约后直接上架。
→ 说明这个需求已被验证有付费需求，也说明**「中文大纲 → 英文成稿」是主流入口形态**（本功能第一版就该从这个入口做起）。

## 2. 目标与非目标

### 目标
1. 把项目内已有的中文小说（`episodes.content`）改写为指定平台 + 品类 + 目标语言的英文稿，**保留中文原稿**。
2. 改写过程可诊断、可分级、可确认、可质检、可断点续跑。
3. 规则库（平台规格 / 品类套路 / 语言层 / 叙事层）**外置为用户可编辑数据**，不写死在代码。
4. 输出一份可直接投稿的英文稿 + 改写说明 + 质检报告。

### 非目标（明确不做）
- ❌ **不做自动投稿**：版权归属与合同风险高（头条那批征稿话题本身就有「绕过平台合同导流」的嫌疑），本功能只出稿。
- ❌ **不做全文机器翻译**：漏译 + 术语漂移已被证实；翻译只作为「语言层」一环，不是主流程。
- ❌ **不做平台数据抓取**：越 ToS，且平台规格做成用户可编辑更可靠。
- ❌ **不覆盖中文原稿**：改写稿独立落库。
- ❌ **不做所有平台所有品类**：第一版只做 3 平台 × 4 品类。

## 3. 领域规则库设计

**核心决策：规则库做成数据文件，由 pipeline 按用户选择动态拼进 prompt；不挂成 Agent skill。**

理由：本仓 `prompts.load_skills()` 会把该 Agent 的**全部** skill（含子目录）一次性拼进 instructions，没有按需加载机制（见 `app/agents/prompts.py:282-302`）。若把 3 平台 + 4 品类都做成 skill，每次调用的 prompt 会膨胀到不可用。做成数据文件 + 按需注入，正好复刻 SoloEnt 的「按品类加载文档」而没有这个坑。

### 3.1 目录结构

```
data/overseas/
├── platforms/
│   ├── dreame.json          # 平台规格
│   ├── goodnovel.json
│   └── webnovel.json
├── categories/
│   ├── werewolf.json        # 品类套路（狼人/ABO）
│   ├── mafia-romance.json   # 品类套路（黑帮言情）
│   ├── billionaire.json      # 品类套路（霸总/亿万富翁）
│   └── systemfic.json       # 品类套路（系统流）
├── language/
│   └── en-US.json           # 语言层规则（称呼/语气/委婉/常见误译）
└── narrative.json           # 叙事层规则（通用，不分平台）
```

`data/` 已在 gitignore 内 → 规则库随用户数据走，不进版本库；仓库内另存一份模板 `app/pipeline/overseas_templates/` 供首次启动播种（比照 `prompts.seed_prompt_files()` 的「仅补缺失不覆盖」策略，已挂在 `app/main.py` 启动流程里）。

> ⚠️ 模板目录**不能**叫 `app/pipeline/overseas/`：同包下 `overseas.py` 与 `overseas/` 同名会造成 import 冲突。

## 4. Pipeline 设计

对齐 drama-adapt 的「五阶段 + 三确认点」，适配本仓 `taskmgr` 线程模型。

### 阶段 0：参数与输入准备（主线程，无 LLM）
- 输入源：本项目的剧集章节（`episodes.content`）或粘贴文本
- 目标平台 / 品类 / 目标语言（默认 en-US）/ 改写级别（auto 或 A/B/C）
- 产出：`overseas_project` 行（状态=init）

### 阶段 1：诊断（LLM）→ **确认点 A**
- Agent：`overseas_analyzer`
- 输入：原文 + 平台规格 + 品类套路 + 叙事层规则
- 输出 JSON：五维诊断（设定/结构/节奏/语言/合规）+ 建议级别（A/B/C）+ 逐条问题清单
- **确认点 A**：用户确认或改级别

### 阶段 2：术语表固化 → **确认点 B**
- LLM 抽取人名 / 地名 / 组织 / 等级体系 / 品类术语 → 生成中英映射表
- **纯数据 + 一次 LLM**，产出存 `overseas_project.glossary_json`
- **确认点 B**：用户可编辑映射表（这是防「同一人名前后不一致」的唯一有效手段，见 §1.1 第 2 条）
- 映射表在后续每次调用都**全量注入**（词表通常几十到几百条，成本可控）

### 阶段 3：结构改写（LLM）→ 产出改写大纲
- Agent：`overseas_analyzer` 复用或新增 `overseas_planner`
- 产出：开篇三章重排、爽点插入位、付费卡点位置（6-8 章）、每章 cliffhanger、章节字数规划
- **确认点 C**（合并到阶段 4 前）

### 阶段 4：正文逐章改写（LLM，串行链式）
- Agent：`overseas_rewriter`
- 每章输入：原文该章 + 结构大纲该章 + 术语表 + 平台/品类/语言/叙事规则片段 + 上一章末尾摘要（保连贯）
- **串行**（本仓铁律：批量生图/生视频必须链式串行；这里同理，避免上下文互相踩）
- 断点续跑：按章落库，`overseas_chapter.status` 记录 done/failed，重跑只跑未完成章
- 产出：英文稿 + 每章的【改写说明】

### 阶段 5：质检（静态 + LLM）
- 静态：`app/pipeline/overseas_check.py`（见 §6）
- LLM：`overseas_qc` 对照 quality-checklist 出报告
- 产出：质检报告（问题分级 + 建议），用户可选择「按报告自动修一轮」

### 任务类型
新增 `taskmgr` 类型：`overseas_diag` / `overseas_rewrite` / `overseas_qc`，全部 `TYPE_SERVICE` 映射到 `"text"`（AI 就绪校验）。
> ⚠️ `taskmgr.submit()` 的 `done_cb` 回调签名是 `cb(task_id, result, error)`（`app/core/taskmgr.py:390`），worker 里绝不能碰 Qt 控件。

### 5.3 调用链（对照现网真实签名）

```python
# app/pipeline/overseas.py
from app.agents.runner import run_agent_json, run_agent      # runner.py:65 / :263

    rules = overseas_rules.assemble(platform, category, "en-US")
    raw = run_agent_json("overseas_analyzer", prompt, lang="zh", config_id=config_id)
    ...
```

**三条必守的调用纪律：**
1. **配置兜底写进函数体**（`config_id = config_id or prose_config_id()`）。AGENTS.md 明确：只写在 UI 层不够，调用点十几处任一漏掉就静默退回全局默认模型。`tests/test_split_models.py` 的断言模式可直接照抄。
2. **runner 的 `system` 覆盖坑**：`runner.run_agent` docstring 明确「workspace 里的提示词是给**带工具的 Mastra Agent** 写的……本仓 runner 是单次调用、没有工具，不覆盖就会拿到一串 `<tool_call>` 文本」。
   → 本功能的 3 个 agent **不挂 skill、不用工具**，提示词按「纯文本输出 JSON」写；调用时仍建议显式传 `system=load_prompt("overseas_analyzer", "zh")` 以免用户改坏了 workspace 文件就跑飞。
3. **文本 config 与生图 config 参数名必须不同**。本轮 P0 就是 `comic_pipeline` 把生图 `config_id` 传给文本调用，导致 `registry.check_ready("text", <生图id>)` 永不匹配 → 每格失败 → 100% 失效且被静默吞掉。
   → 本功能签名统一 `text_config_id`（规划侧可另给 `plan_config_id`），**不要叫 `config_id`**。

## 6. 静态校验器（`overseas_check.py`）

规则全部来自 §1.2 / §1.3，可静态检测、不依赖 LLM。**这是本功能相对竞品的核心差异点**（竞品只有 LLM 质检）。

| # | 规则 | 判据 | 来源 |
|---|---|---|---|
| R1 | 第一视角自我观察违背 | 正则命中「我的脸红了/我的眼睛红了/我的脸色/我的表情/我的脸发烫」等自指外观描写 → 报违规 | 头条第三篇 |
| R2 | 第一视角被动链 | 连续 ≥3 段呈「看到→感觉→反应→等待」结构（无判断/决定/行动动词） | 头条第三篇 |
| R3 | 赘述 | 相邻句重复度 / 形容词密度超阈 / 内心独白循环 | 头条第三篇 |
| R4 | 中文残留（漏译检测） | 英文输出里含 CJK 汉字或中文标点「，。、；：」 | 童晔「漏译」 |
| R5 | 人名/术语一致性 | 术语表里的中文名，其对应译名未出现在译文中 → 报冲突 | 童晔「同一人名翻译不一致」 |
| R6 | 章节字数越界 | 超出平台 `chapter.min_words/max_words` | 平台规格 |
| R7 | 付费卡点位置 | 卡点章节不在平台 `paywall.paywall_chapter_range` | 头条/zenstory |
| R8 | 开篇三章爽点 | 第 1-3 章缺「爽点四拍」（看不起→低调→大佬打脸→跪了 任一）的标记 | 头条爽点公式 |
| R9 | 章节结尾钩子 | 章末无开放问题/倒计时/反转/未完成动作 → 报缺失 | zenstory 13 种钩子 |
| R10 | 翻译腔 | 单句 >35 词 / 被动语态占比过高 / 连接词堆叠 | 头条本土化篇 |
| R11 | 章末「任务—奖励」闭环 | 男频品类下章末无收益/进度反馈 | 头条品类篇 |

**与现有 `novel.check_pov_violation()` 的关系：不要混用。**
`check_pov_violation`（`app/pipeline/novel.py:1194-1210`）是**粗粒度人称漂移**检查（数「我」和「他/她」的次数），R1/R2 是**细粒度自我观察/主动性**检查，语义完全不同。R1/R2 写成独立函数 `check_first_person_self_observation()` / `check_first_person_passivity()`，不要去改 `check_pov_violation`（它在小说线有回归测试保护，且会误伤）。

**误伤控制**：所有规则只做高置信判断，宁可漏报不误报（沿用 `check_pov_violation` 的既定口径）。

## 7. 数据落库

**新增 2 张表**（不动 `dramas` 表，避免污染现有 23 表 schema）：

```sql
CREATE TABLE IF NOT EXISTS overseas_project (
    id            INTEGER PRIMARY KEY,
    drama_id      INTEGER NOT NULL,
    platform      TEXT NOT NULL,        -- dreame / goodnovel / webnovel
    category      TEXT NOT NULL,        -- werewolf / mafia-romance / billionaire / systemfic
    target_lang   TEXT NOT NULL DEFAULT 'en-US',
    level         TEXT NOT NULL,        -- A / B / C
    status        TEXT NOT NULL,        -- init / diagnosed / confirmed / rewriting / done / failed
    glossary_json TEXT DEFAULT '{}',    -- 中英映射表
    plan_json     TEXT DEFAULT '{}',    -- 阶段3 结构大纲
    diag_json     TEXT DEFAULT '{}',    -- 阶段1 五维诊断
    created_at    TEXT, updated_at TEXT
);

CREATE TABLE IF NOT EXISTS overseas_chapter (
    id           INTEGER PRIMARY KEY,
    project_id   INTEGER NOT NULL,
    episode_id   INTEGER,               -- 对应原中文章节（可空：粘贴文本导入时为空）
    chapter_no   INTEGER NOT NULL,
    title        TEXT,
    content      TEXT,                  -- 英文改写稿
    notes        TEXT,                  -- 【改写说明】
    words        INTEGER,
    qc_json      TEXT DEFAULT '{}',
    status       TEXT NOT NULL DEFAULT 'pending',  -- pending/done/failed
    updated_at   TEXT
);
```

**为什么不复用 `dramas.novel_meta`**：`novel_meta` 是小说线的 JSON 袋（`db.py:146`），塞海外改写状态会与小说线状态互相覆盖，且无法按章查询/断点续跑。独立表更干净。
**为什么不复用 `episodes.content`**：改写稿是英文双版本，**必须保留中文原稿**（AGENTS.md 反复强调不破坏用户数据）。

### 7.1 多平台并行（同一篇稿子出多个平台版本）

实测：**换平台只变规则片段的 25 行**，而且变的全是三块 —— ①商业规格（签约门槛/更新节奏/付费卡点）②读者画像与文风（段落密度、口语度、章末钩子强度、审核尺度）③标题风格与禁止项。**不变的是**本土化三层、第一视角硬约束、付费卡点方法论。

所以数据模型要按「哪些随平台变、哪些不随平台变」切：

```
overseas_project        源项目(与平台无关)
  ├── drama_id / target_lang
  ├── glossary_json     术语表  ← 人名译名不因平台而变,放这层,只抽一次
  └── diag_json         五维诊断 ← 语言层问题平台无关,只诊断一次
      │
      └── overseas_variant      平台变体(随平台变)
          ├── platform / category / level
          ├── plan_json         章节切分 + 卡点位置 + 开篇重排(按平台算)
          └── overseas_chapter  英文改写稿(按平台产出)
```

- 术语表与诊断在 **project 层**：同一篇中文稿，三个平台的「林晚」必须译成同一个名字，没必要抽三次。
- 章节切分、卡点位置、文风适配在 **variant 层**：GoodNovel 要 800-1500 词、卡点第 6-8 章；Webnovel 日更 1500 字，章节更短、卡点规则不同。
- 实现顺序建议：先做单平台（`overseas_project` 直接带 platform 字段），把 `overseas_variant` 留到用户真需要「一篇稿出三平台」时再拆 —— 早拆会多写一半表和迁移代码。

### 7.2 加一个新平台要做什么

**只加一个 JSON**：`data/overseas/platforms/<id>.json`（或 `app/pipeline/overseas_templates/platforms/<id>.json` 供随版本分发），字段照抄现有三个，填：

| 字段 | 作用 |
|---|---|
| `signing` / `updates` / `rewards` | 商业规格：签约门槛、更新节奏、奖励阶梯 |
| `paywall.paywall_chapter_range` | 付费卡点允许的章节区间（留空则不做 R7 检查） |
| `opening.payoff_within_chapters` | 开篇几章内必须释放爽点 |
| `chapter.min_words/max_words` | 章节字数区间（喂 R6） |
| `style_notes` | **读者画像 + prose 文风 + pacing 节奏 + review_tolerance 审核尺度** |
| `title_style` / `banned` | 标题风格与禁止项 |
| `source` / `source_verified` | 数据出处与「是否已核实」标记（平台规格都是二手数据，必须标） |

品类同理，加 `data/overseas/categories/<id>.json`（必备元素 / 桥段 / 术语种子 / 爽点关键词 / 任务—奖励标记 / 禁止项 / 写法要求）。

改完立即生效，**不需要改任何代码** —— `assemble()` 按 id 取数据。

## 9. i18n（16 语言）

- **界面文案**：走 `app/core/i18n.py` 的 `Z`（英文键 → 中文基准）+ `app/core/ui_strings.py` 的 `S`（同一英文键 → 15 语言 list）；繁体补 `T["zh-Hant"]`。顺序 `zh en ja ko ar hi id th tr vi fr de es pt it`。这两个文件是 **CRLF、无 BOM**，改时必须保 CRLF。
- **⚠️ 目标语言是独立的第三个开关**：`set_language` 同时控制界面语言与 AI 内容语言（`content_language` 设置项）。海外改写目标语言**必须新开一个设置**（如 `overseas.target_lang`），绝不能复用 `content_language`——否则用户选了 en-US 会把整个 App 界面切成英文。
- **Agent 提示词语言决策：只用中文基准，不做 16 语言变体。**
  理由：海外平台术语（fated mate / mate mark / ABO）本来就是英文，规则知识用中文写更准确；做 16 份规则文件等于 64 个文件的维护成本，且规则一变要同步 16 处。界面语言 ≠ 规则语言。
  → 调用时 `lang="zh"` 载入提示词（`load_prompt` 只在 `lang != "zh"` 时追加输出语言后缀，所以传 zh 就不会强行锁英文），**输出语言由 pipeline 在 user_prompt 里显式指定为目标语言**。

## 12. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 平台规格数字二手、互相矛盾、且会变 | 高 | 规则库外置为用户可编辑数据；每条规则带 `source` 字段；UI 显式提示「非官方数据，请复核」 |

| 触犯今日头条那批征稿渠道的私域导流 | 中 | 本功能不提供任何投稿渠道对接；只出稿 |

| `templates/language/en-US.json` | 称呼表/语气词/委婉语/常见误译/标点/自我观察禁写式/章末钩子标记/翻译腔阈值 |
| `templates/narrative.json` | 本土化三层/第一视角硬约束/付费卡点倒推 5 步 + 6 条失败修正/A·B·C 改写级别/质检清单 |

关键 API：
- `seed_templates()` — 播种，**只补缺失不覆盖用户改动**
- `list_platforms()` / `list_categories()` — 给 UI 下拉
- `get_platform(id)` / `get_category(id)` / `get_language(lang)` / `get_narrative()` — 缺项抛 `RuleError` 并列出可用值
- `glossary_seed(category_id)` / `chapter_bounds()` / `paywall_range()`
- `validate() -> list[str]` — 结构体检（不抛异常，UI 可直接展示）
- `assemble(platform_id, category_id, level=..., target_lang=...) -> str` — **按需拼装**，只拼选中的平台 + 品类

实测：拼出的规则片段约 3000 字，`assemble("goodnovel","werewolf")` 中**不含** Dreame/霸总/黑帮言情（未选中的内容不会漏进 prompt）。

**跑真链路才暴露的两个误报**（单元测试全绿也照样漏）：

1. **R4 误报英文弯引号** —— 真实英文稿全篇用 `“ ”` 展开引号，早期版本把它们列进「全角中文禁用集」→ 整篇误报。
   → 修：禁用集只留中文独有的 `，。、；：！？（）【】《》〈〉「」～`；`“ ” ‘ ’ — …` 是英文正规排版，不算问题。
2. **R9 误报真实钩子** —— 改写稿收尾「The access panel beside them began to blink red.」是标准断点，但钩子标记表没收录 `began to`。
   → 修：钩子标记补 `began to / started to / was about to / one more / not until / the sound of / had not`，并加兜底集（语言规则文件没给时用内置集）。

> 另：规则库「只补缺失不覆盖」是双刃剑 —— 改了模板不会自动同步到已播种的副本。
> → 补 `seed_templates(force=True)`：供「恢复默认规则库」用，也供模板升级刷新未被改过的副本。
