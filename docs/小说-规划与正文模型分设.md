# 小说线:规划模型与正文模型分设

## 一句话

小说生产的所有 AI 调用被拆成两档,**结构化的走「规划模型」,写长篇正文的走「正文模型」**,两个下拉在「小说策划与设定」面板顶部,各自记住选择。

## 为什么要分

同一批章节计划,拿两个模型各写第 1–3 章,实测结果:

| 模型 | 三章总字数 | 逐章字数 | 结论 |
|---|---|---|---|
| minimax-M3 | 6538 | 1988 / 2638 / 1912 | 篇幅稳定,无衰减 |
| deepseek-v4-pro | 5332 | 2513 / 1640 / 1179 | 逐章衰减 **53%** |

deepseek 开篇最好、后面掉一半,长篇会越写越短到不可用;minimax 正好相反,篇幅可控。

规划侧则相反:生成「分卷战略」「故事合约」这类要回填结构化字段的内容时,deepseek-v4-pro 的 JSON 更规整 —— 7 卷的目标 / 关键事件 / 钩子字段齐全,minimax 偶尔只吐一段散文。

一个模型干不了两头,所以拆开。

## 谁走哪个模型

**规划模型**(`app/pipeline/novel.py:plan_config_id()`,配置键 `yihao.novel.plan_cfg`)

- `plan_novel` 开书策划
- `plan_chapters` 逐章计划(单次)
- `plan_characters` 主要角色
- `draft_section` 总纲 / 世界观 / 故事合约 / 角色设定 / 卷战略 / 章节规划 六块
- `draft_volume_in_batches` 分卷骨架 + 逐卷展开
- `generate_chapters_for_volume` 按卷生成章节计划
- `generate_chapters_batched` 全书分批生成章节计划

**正文模型**(`prose_config_id()`,配置键 `yihao.novel.prose_cfg`)

- `write_chapter` 章节正文
- `write_chapter_with_review` 写章 → 校验 → 审校 → 重写整条链
- `review_chapter` 六维审校
- `edit_chapter` 按指令改稿
- `gen_chapter_title` 一键章节名

## 怎么改

**界面上**:项目 → 小说策划与设定 → 面板最上方一行,「规划模型」「正文模型」两个下拉。改完立刻生效,选择写进配置,下次打开还在。

**没选过怎么办**:各自回落到全局默认文本模型(`registry.default_config("text")`),所以不选也能跑,只是拿不到分设的收益。

**默认值**:新装的库预设为 规划 = deepseek-v4-pro,正文 = minimax-M3。

**命令行 / 脚本调用**:两个函数都接受显式 `config_id`,传了就用传的,不传才回退。UI 是走「不传 → 内部兜底」这条路,所以下拉的选择对所有入口都生效。

## 实现要点(给改代码的人)

兜底写在**每个入口的函数体内**(`config_id = config_id or plan_config_id()`),不是只写在 UI 层。

原因:调用点有十几处(UI、批量、程序化脚本),任一处漏掉兜底,那个入口就会静默退回全局默认模型 —— 用户在界面上选了规划模型,却在批量入口写正文时用了默认模型,而且**界面上看不出任何异常**。

`tests/test_split_models.py` 里 `test_every_planning_entry_falls_back_to_plan_model` 和 `test_every_prose_entry_falls_back_to_prose_model` 逐个断言源码里含对应兜底调用,新增入口时会被这两条测试逼着补上。

UI 侧曾经踩过一个具体的坑:`novel_dialogs._draft_section` 读的是 `self.text_combo`,该控件被两个新下拉取代后 `hasattr` 恒为 False,于是永远传 `None`,规划模型的选择形同虚设。现在读的是 `self.plan_model_combo`。

## 相关配置键

| 键 | 用途 |
|---|---|
| `yihao.novel.plan_cfg` | 规划模型配置 id |
| `yihao.novel.prose_cfg` | 正文模型配置 id |
