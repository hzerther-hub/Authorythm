## 一、Bug 现象与根因

### 现象

某个分镜的��频生成任务**永久停在「生成中」**，界面刷新、重启服务都不消失，���续数小时。

实测记录（参考项目）：任务 `sys_task.id=1105`，`storyboard_id=137`（分镜 06），
`created_at = 17:02:56`，到 23:22 仍是 `processing`，已挂 **6 小时 20 分钟**。

### 根因（三层叠加）

1. **`task_id` 为空**——任务在「向 AI 厂商提交生成请求」这一步就失败了，从未拿到任务句柄。
   空句柄意味着**既没有轮询、也没有回调**会再来更新它，状态就此永久冻结在 `processing`。

2. **兜底只在启动时跑一次**——`settle_interrupted_tasks()` 仅在 `init_db()` 里调用一次。
   如果孤儿任务产生于这次清理**之后**（服务运行期间提交失败/崩溃），就再没有任何机制回收它。

3. **重试循环缺总时长闸门**——`max_attempts=20` 只约束**次数**不约束**时长**，
   而跟随上游 `Retry-After` 的分支（`retry_at_wait_seconds`，最多跟 2 次、单次 ≤24h）
   会让单次尝试的等待远超常规退避。20 次尝试理论上可累积出数小时，过程中没有任何时间闸门。

> 注：pydrama 的 `_generate_with_retry()` 里 `started = _t.time()` **没有**被重置，
> 比参考项目（`startedAt = Date.now()` 每次跟随 Retry-At 都重置）更严谨，
> 因此**第 3 点在 pydrama 的危害小于参考项目**。仍建议加闸门做纵深防御——
> 防止将来新增的重试分支重蹈覆辙。

### 同批任务的对照证据

参考项目里同批次其它任务都留下了明确失败原因，唯独 1105 没有任何失败记录：

| 任务 | storyboard | 结果 | 说明 |
|---|---|---|---|
| 1090/1091/1093/1094/1097 | 138/141/143/144/139 | failed | 「创建请求重试超过 1800s 未成功（上游持续无响应）」——被超时机制兜住了 |
| 1100–1104 | 135/138/139/143/144 | completed | 正常完成 |
| **1105** | **137** | **processing 6h+** | `task_id=null`，无任何失败记录——**漏网的那一个** |

## 二、需要改的地方

### 改动 1：`app/ai/video_client.py` — 重试循环加总墙钟闸门

**位置**：`_generate_with_retry()`，约 629–676 行。

现状（第 671 行）：
```python
if elapsed + wait > budget or attempt == max_attempts - 1:
    raise VideoRetryExhausted(attempts, last_err)   # 预算耗尽或次数用尽
```
`budget` 是**单轮预算**（普通 180s / 限流 1800s），会被限流模式抬高，
但没有任何「从首次尝试起算的总时长」上限。

**加法**：

```python
# 创建请求的总墙钟上限：无论预算怎么升档、Retry-After 跟几次，
# 从首次尝试起算的总时长不得超过它。max_attempts 只约束次数不约束时长，
# 上游每次都返回一个未来的 Retry-After 就能让 20 次尝试累积出数小时。
# 取 2 小时：覆盖限流长预算(30min) 之外的所有正常情况。
CREATE_TOTAL_WALL_CLOCK_S = 2 * 60 * 60
```

在 for 循环**开头**（每轮 attempt 进入时）插入：

```python
first_attempt_at = _t.time()   # 循环外初始化，总墙钟起点
...
for attempt in range(max_attempts):
    if _t.time() - first_attempt_at >= CREATE_TOTAL_WALL_CLOCK_S:
        raise VideoRetryExhausted(
            attempts,
            RuntimeError(f"创建请求累计超过 {int(CREATE_TOTAL_WALL_CLOCK_S/60)} 分钟仍未成功，已按总时长上限失败"),
        )
```

要点：起点用**独立变量** `first_attempt_at`，不要复用 `started`
（`started` 语义是当前预算轮起点，将来若引入预算重置会被污染）。

异常文案建议与参考项目保持一致，便于跨项目排查：
`创建请求累计超过 120 分钟仍未成功，已按总时长上限失败`

### 改动 2：`app/core/db.py` — 收尾逻辑加上运行期周期巡检（**关键**）

**位置**：`settle_interrupted_tasks()`，约 538–560 行；调用点 `init_db()` 第 409 行。

现状：函数本身写得没问题（按产出归位，而非一律标 failed，这点是对的，保留），
但**只在启动时执行一次**，运行期新生的孤儿无人回收。

**加法**：

**(a) 启动调用延迟** — 避免误伤本进程刚提交、正在正常生成的任务。
把 `init_db()` 第 409 行的直接调用替换为延迟调用：

```python
# 延迟一点再首次收尾：给本进程刚提交的任务留出落库时间
_TASKS.setDaemon(True) if hasattr(_TASKS, "setDaemon") else None
threading.Timer(10.0, lambda: settle_interrupted_tasks(db, now(), reason="启动清理")).start()
```

若不想在 `init_db()` 里引线程，退一步的做法：保持同步调用但在函数内
**跳过 `created_at` 距今不足 N 分钟的任务**（N 取 10 分钟），效果等价且无线程开销。
**二选一即可，不要两者都做。**

**(b) 运行期周期巡检** — 这是真正堵住漏洞的一步：

```python
REAP_INTERVAL_S = 45 * 60   # 45 分钟

def start_stuck_task_watchdog(db):
    """周期巡检僵尸任务。

    settle_interrupted_tasks 只在启动时跑一次，而孤儿任务常产生于运行期
    （提交上游阶段崩溃、超时判定丢失），届时无人回收，界面永远显示"生成中"。

    间隔必须大于单次生成的正常时长（视频最久 ~30min），只捞真正僵死的。
    """
    def _tick():
        try:
            settle_interrupted_tasks(db, now(), reason="运行期巡检")
        except Exception as exc:
            print(f"[watchdog] 巡检失败: {exc}")
        finally:
            t = threading.Timer(REAP_INTERVAL_S, _tick)
            t.daemon = True
            t.start()
    t = threading.Timer(REAP_INTERVAL_S, _tick)
    t.daemon = True
    t.start()
```

在应用启动处（`main.py` 或 `app.py` 中 `init_db()` 之后）调用一次 `start_stuck_task_watchdog(db)`。

**要点**：
- **间隔 45 分钟不可压到 30 分钟以下**——视频生成正常时长约 30 分钟，
  巡检太密会误杀正在正常生成的任务。
- 线程必须 `daemon=True`，否则程序退不出。

**(c) 错误文案** — 现为「服务重启，生成任务中断，请重试」，但运行期巡检也会触发，
  措辞会误导。改为：

```python
"任务已失去回执（服务重启或提交中断），请重试"
```

## 三、验收标准

1. **构造孤儿任务**：手动往 `sys_task` 插一条 `status='processing'` 且 `task_id=NULL` 的记录，
   同时插一条 `storyboards.status='processing'` 且 `video_url` 为空的记录。
2. 等待巡检（或临时把 `REAP_INTERVAL_S` 调小验证），
   确认两条都被归位为 `failed`，界面不再显示「生成中」，且**重试按钮可用**。
3. **确认不误伤**：启动一个正常的长时间视频生成，确认在 45 分钟巡检窗口内
   它不会被标成 failed（这是本改动最大的回归风险，务必验证）。
4. `_generate_with_retry` 的总墙钟闸门：把 `CREATE_TOTAL_WALL_CLOCK_S` 临时改小，
   确认能在该时长内抛出 `VideoRetryExhausted` 而非无限重试。
5. 正常生成的图片/视频任务不受影响，重启后既有行为与改动前一致。

---

## 四、注意事项

- **不要**把巡检改成「只查 `task_id IS NULL` 的任务」。理由：轮询中断但已拿到句柄的
  任务同样会僵死（参考项目里 1092/1095/1096/1098/1099 就是
  `task_id` 有值却因服务重启而僵死的），口径必须是**全部 `processing`**。
- 「有产出 → completed，否则 → failed」的归位逻辑是对的，保持不变。
- 若将来引入更多任务类型（如 `comic`），`_settle_storyboard_status` 的覆盖面
  可能需要相应扩展——但不要在本任务里做。
