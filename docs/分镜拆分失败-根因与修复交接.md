## 二、根因（已用代码 + 数据双向证实）

### 证据链

1. `app/ai/text_client.py:51` — 输出预算的最终兜底
   ```python
   body["max_tokens"] = mt or 8192
   ```
2. 用户当前选中的文本模型是 **minimax-M3**（`app_settings` 里 `yihao.model.text = '4'`），
   该配置 `max_tokens` 字段为 **None** → 实际只发 **8192**
3. `app/pipeline/storyboard.py:96` 调用 `run_agent_json` 时**没有传 `max_tokens`**
4. minimax-M3 是推理型模型，会先吐 `<think>` 思维链；分镜提示词本身极大
   （剧本 `script[:14000]` + 资产清单 + 约 40 行硬规则）
   → **8192 全被 `<think>` 吃光，正文 JSON 一个字没开始写就被截断**
5. 修复前的 `run_agent_json` 重试**用的是同一个 8192**（`runner.py:128`），
   等于拿同样的截断结果再赌一次 → 必然二次失败

### 决定性的一条

```bash
git log -S 'max_tokens' -- app/pipeline/storyboard.py
# (空)
```

**`max_tokens` 在 `storyboard.py` 的整个 git 历史里从未出现过。** 不是回归，是一直没修。

### 为什么"有些路径能成功"

| 路径 | 预算来源 | 结果 |
|---|---|---|
| `extractor.py:92` | 显式 `EXTRACT_MAX_TOKENS = 32768` | ✅ 已修（提交 `bb284d6`） |
| `novel.py` 章节计划 | `_plan_budgets()` 阶梯 | ✅ 已修（提交 `db81842`） |
| `novel.py:976` 正文 | `(配置值 or 32768, 32768, 32768)` | ✅ 已修 |
| `storyboard.py:96` | 无 → 回落 8192 | ❌ 一直坏 |

库里那两条 `extract` 失败记录是 `bb284d6` **修复之前**的历史数据，现在不会再复现。

### 模型实测（2026-10-18，用项目自身配置打的探测）

| 模型 | 配置 max_tokens | 发 131072 | usage 里的推理 token |
|---|---|---|---|
| deepseek-v4-pro | 32768 | 接受 | `reasoning_tokens: 28` |
| minimax-M3 | None | 接受 | `reasoning_tokens: 41` |

**两家都是推理型模型，且网关都不拒绝大 `max_tokens`。**

## 三、已实施的修复：模型无关的预算自适应

用户明确要求：**不能针对某个模型调参，要做成通用的。**
所以没有沿用"硬写 32768"（那是给 minimax 调参，换家供应商又得重调）。

### 改动文件

`app/agents/runner.py` —— 改在 `run_agent_json` 这一层，**一处覆盖全部 JSON 类 Agent**
（storyboard / comic / promo / novel_reviewer / prompts_gen 等 20+ 处调用点）。

### 核心设计

**用"输出是否被截断"这个客观信号决定升不升预算**，而不是猜某个模型需要多少：

```python
def _looks_truncated(raw: str | None) -> bool:
    """输出是否像是被输出预算截断。三个信号：
       1. 空响应            —— 预算全烧在 <think> 上，正文一字没写
       2. <think> 未闭合    —— 还在思考就被切断
       3. JSON 括号不配平   —— 正文写到一半被切断
    """
```

命中才升预算；否则（JSON 写坏 / 模型回了工具调用 / 输出散文）**升预算纯属浪费 token**，
走既有的禁工具重试。

预算阶梯：`8192 → 16384 → 32768 → 65536`（`BUDGET_FACTOR = 2`，`BUDGET_CEILING = 65536`）

**天花板由供应商自己告诉我们** —— 中途遇到 `AIError`（通常 400 表示拒绝该预算）就把阶梯
压回上一档，而不是在代码里写死某家的上限。

起始预算优先级与 `novel._configured_max_tokens`、`text_client._build_body` 保持一致：
**调用方显式值 > 服务配置里手填的值 > 8192**。

### 为什么这样是通用的

- 非推理模型：输出本来就不是截断的 → 不触发升级，行为与改动前完全一致
- 任意推理模型：无论需要多少预算都能自己爬到够用为止，**不需要单独调参**
- 换供应商：上限靠 400 反馈自适应，不写死

### 已验证（`tests/test_agent_budget.py`，18 个用例全绿）

| 场景 | 期望 | 实测 |
|---|---|---|
| 被截断 | 阶梯升预算直到成功 | `[8192, 16384, 32768]` ✅ |
| JSON 写坏（未截断） | 不烧预算，走禁工具重试 | `[8192, 8192]` ✅ |
| 模型回工具调用 | 同上，预算不抬 | `[8192, 8192]` ✅ |
| 中途 400 | 天花板压回上一档继续 | `[8192, 16384, 8192]` ✅ |
| 起始档就 400 | 供应商侧硬错误，原样抛出 | ✅ |
| 调用方显式预算 | 作为**起始**值，不被跳过 | `[4096, 8192, 16384]` ✅ |
| 一次成功 | 只调一次，不浪费 | `[8192]` ✅ |
| 升到天花板仍截断 | 报错，不无限升级 | 封顶 65536 ✅ |
| 提示词加载失败 | 不掩盖真正的 JSON 解析报错 | ✅ |

**一个刻意明确的契约：`max_tokens` 是「起始」预算而不是上限。**
否则调用方就得自己知道"这个模型需要多少预算"，那就退回到为每个供应商调参的老路。
本仓调用方（`extractor` 显式传 32768）传的是"至少要这么多"而非"最多花这么多"，升级不违背其意图。

顺带修掉一个健壮性问题：阶梯失败后的禁工具兜底里，`prompts.load_prompt()` 若抛异常
（Agent 名拼错 / 提示词文件缺失）会**掩盖真正的 JSON 解析失败**。现在这类异常被吞掉，
保证最终抛出的仍是 `输出无法解析为 JSON:...`，诊断信息不丢。

## 十、二次修复(同日 21:5x):自适应上线后仍然失败的两个新坑

第一次修完(提交 `42d7b38`)、用户在 UI 上重跑仍然 `failed`,`storyboards` 依旧 0 行。
用真实 prompt 做了一次只读探针(不落库,DB 先复制到临时目录):

| 档位 | finish_reason | completion_tokens | 结果 |
|---|---|---|---|
| 65536 | `stop` | **50,787** | 26 镜、115,433 字符、`extract_json` 成功 |

也就是说模型本身能写完,问题出在「升预算的判定」和「超时」两处:

### 坑 1:只按括号配平判定截断,会漏

`_looks_truncated` 原来是「`{` 多于 `}` 就认为被切断」。实测 8192 档的输出
**恰好切在 JSON 字符串中间**,此时 `{` 与 `}` 数量相等 → 判定「没截断」→
不升预算,直接走禁工具重试(还是 8192)→ 必然再失败。
时间也对得上:失败任务总共 166s,根本不够跑完 65536 档(单次实测 401s)。

**改法**:`text_client.chat(with_meta=True)` 把 `finish_reason` 透出来,
`_looks_truncated(raw, finish_reason)` **优先信 `finish_reason == "length"`**,
括号/`<think>` 只作供应商不给该字段时的退化判断。

### 坑 2:大预算必然撞 300s 超时

实测 50,787 tokens 用了 401s(≈127 tok/s),而 `AI_LLM_TIMEOUT_S` 默认 300s。
就算升到 65536 也只会得到 `requests.Timeout` —— 它不是 `AIError`,
会直接冒到任务里,报错看起来和「模型不会写 JSON」毫无关系,极难归因。

**改法**:`_timeout_for(budget) = max(AI_LLM_TIMEOUT_S, budget // 60 + 120)`,
65536 档给 1212s。

### 顺手做的两件事

- `storyboard.split_storyboards` 直接以 `STORYBOARD_MAX_TOKENS = 65536` 起步
  (按实测 26 镜/50,787 tokens 定),不再白烧 8192→16384→32768 三档(≈16 分钟)。
- 起始预算被供应商 400 拒绝时(`_budget_rejected`)退回 `BUDGET_START` 重爬,
  而不是直接抛 —— 调用方按「输出大」填的高预算,供应商不认不代表配置坏了。

### 实测复核

- `tests/test_agent_budget.py` 24 例(新增 finish_reason / 超时缩放 / 高预算被拒回退);
- 全量 `pytest tests/` → 326 passed / 5 skipped。

## 十一、三次修复:改为按场景分批(最终方案)

第二节之后,把预算抬到 65536 + 信 `finish_reason` 后,用户在 UI 上重跑仍然失败。
日志给出了决定性证据:

```
agent.budget.attempt agent=storyboard_breaker budget=65536 finish=length
    out_tokens=65536 chars=128980 truncated=True
```

也就是**供应商把 65,536 全吐满了还是没写完**。而同一 prompt 的只读探针上一次只用了
50,787 tokens 就 `stop` —— 输出长度**波动极大**,单一「足够大」的预算不存在。

### 方案:按场景切批,每批一次调用

- `storyboard._script_batches()`:按 `## S\d+|` 场景头切块,再按
  `STORYBOARD_CHUNK_CHARS = 1400` 合并成批;末尾过短的场次并入相邻批
  (实测 ep2 的 S06 只有 189 字,单独发一次调用纯浪费)。
- 每批 prompt 只有本批剧本 + 完整资产清单 + 同一份格式规范,并追加一段
  「只输出本批、镜号从 1 起、不要重复前批」的说明。
- 落库前按批顺序重新编号 1..N —— 不能依赖跨批的原始 `number` 排序。
- `split_storyboards(..., on_progress=)` 每批完成后回报进度,
  `split_storyboards_bg` 把它接到 `TM.set_task_progress`,任务面板不再 0% 卡 10 分钟。

### 为什么不是继续抬预算

- 128k 档单次要 ~15 分钟,且仍可能超;
- 分批后单批输出约 1/2-1/3,既留足余量,也把「一次失败全丢」变成「只重跑那一批」。

### 实测

- ep2(2,959 字 / 8 场)切成 2 批:第 01-06 场(1,564 字)+ 第 07-08 场(1,396 字);
- `tests/test_storyboard_chunking.py` 7 例(不丢字、不切场、短场合并、分批提示);
- 全量 `pytest tests/` → 339 passed / 5 skipped。
